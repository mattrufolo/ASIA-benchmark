# ASIA Benchmark Study: Agentic AI in System Identification

This repository contains the code accompanying the paper:

> M. Rufolo, D. Piga, and M. Forgione, *Agentic AI in System Identification: An Extensive Benchmark Study*, 2026.

[ASIA](https://github.com/dariopi/ASIA) is an agentic AI framework for system identification. An LLM acting as an autonomous coding agent iteratively proposes, implements, and evaluates modelling and training configurations under a fixed, immutable evaluation protocol. The framework is built on the [autoresearch](https://github.com/karpathy/autoresearch) platform and is described in:

> D. Piga and M. Forgione, *ASIA: an AI Agent for System Identification*, 2026.

In this study, ASIA is extended from two case studies to ten benchmarks from the [Nonlinear Benchmark](https://www.nonlinearbenchmark.org/) repository, all run under the same protocol: a one-hour training budget per run and up to 20 runs per search. Compared with the original study, the agent is Claude Code with Claude Sonnet 5, and each benchmark additionally ships a white-box model following the physics-based description of the corresponding reference paper. The agent can keep and tune it, drop it, or turn it into a grey-box structure.

# Repository

This repository contains one self-contained project per benchmark:

| Folder | Benchmark |
|---|---|
| `Bouc_Wen` | Bouc-Wen hysteretic system |
| `WH` | Wiener-Hammerstein |
| `Parallel_WH` | Parallel Wiener-Hammerstein |
| `WH_Process_Noise` | Wiener-Hammerstein with process noise |
| `EMPS` | Electro-Mechanical Positioning System |
| `CED` | Coupled Electric Drives |
| `Industrial_Robot` | Industrial Robot Arm |
| `Silverbox` | Silverbox |
| `Fine_Steering_Mirror` | Fine Steering Mirror |
| `F16` | F-16 ground vibration test |

Each subfolder has its own data preparation, model definition, training loop, evaluation script, and benchmark-specific documentation.

> **Note on the Industrial Robot Arm.** The size of the `Industrial_Robot` project, once its checkpoints are included, exceeds the limits allowed by GitHub. For this reason, it is not stored in this repository: it will be provided together with its checkpoints as a separate download, available at the release section of the repository.

## Repository Organization

Every benchmark subfolder follows the same structure:

- `prepare.py`: prepares the benchmark data, cached files, and cross-validation folds (fixed, not edited by the agent)
- `model.py`: defines the model architecture (edited by the agent)
- `train.py`: runs the training and cross-validation loop (edited by the agent)
- `test.py`: evaluates the saved checkpoints on the official test data
- `PROGRAM.md`: task description and rules of the autonomous search, including the main modelling insights of the benchmark's reference paper and a pointer to the white-box implementation
- `README.md`: benchmark-specific details
- `pyproject.toml` and `uv.lock`: define and lock the Python environment

## Repository Branches

The repository has two branches:

- `main`: starting point of each benchmark, before any autonomous experimentation (task descriptions, fixed scripts, starting black-box and white-box models)
- `final`: final state after the agent completed the search on each benchmark (agent-written code, search journals, results)

```
git checkout main   # starting point
git checkout final  # code generated by the agent, journals and results
```

Re-running the training of a selected model is reproducible. The search itself is not: being driven by a stochastic LLM, the same instructions may produce a different sequence of attempts.

## Benchmarks and References

Seven benchmarks come with a standardised testing procedure and a public leaderboard, defined at <https://www.nonlinearbenchmark.org/results-reporting>. For the other three (Bouc-Wen, WH with process noise, Industrial Robot Arm) we adopt the train/test split and metric of the respective reference papers.

- **Bouc-Wen**: M. Schoukens and J. P. Noel, *Three Benchmarks Addressing Open Challenges in Nonlinear System Identification*, IFAC-PapersOnLine, 50(1), 2017.
- **Wiener-Hammerstein**: J. Schoukens and L. Ljung, *Wiener-Hammerstein benchmark*, 2009.
- **Parallel Wiener-Hammerstein**: M. Schoukens, A. Marconato, R. Pintelon, G. Vandersteen, and Y. Rolain, *Parametric identification of parallel Wiener-Hammerstein systems*, Automatica, 51, 2015.
- **Wiener-Hammerstein with process noise**: M. Schoukens and J. P. Noel, *Three Benchmarks Addressing Open Challenges in Nonlinear System Identification*, IFAC-PapersOnLine, 50(1), 2017.
- **EMPS**: A. Janot, M. Gautier, and M. Brunot, *Data set and reference models of EMPS*, 2019.
- **Coupled Electric Drives** and **Silverbox**: T. Wigren and J. Schoukens, *Three free data sets for development and benchmarking in nonlinear system identification*, ECC 2013.
- **Industrial Robot Arm**: J. Weigand, J. Gotz, J. Ulmen, and M. Ruskowski, *Dataset and baseline for an industrial robot identification benchmark*, 2023.
- **Fine Steering Mirror**: M. Floren, L. Peri, J. De Maeyer, W. De Munter, D. Vandepitte, and J. P. Noel, *Data-driven state-space identification and nonlinearity assessment of the CubeSpec fine steering mirror*, ISMA-USD 2024.
- **F-16**: J. P. Noel and M. Schoukens, *F-16 aircraft benchmark based on ground vibration test data*, 2017.

## Typical Workflow

The workflow is the same for all benchmarks.

1. Install `uv` if it is not already available:

```
curl -LsSf https://astral.sh/uv/install.sh | sh
```

2. Move into the benchmark folder you want to run (the example uses `WH`):

```
cd WH
```

3. Sync the project environment:

```
uv sync
```

4. Prepare the cached data, folds, and evaluation metadata:

```
uv run prepare.py
```

5. Run a one-shot training pass to verify that the setup works:

```
uv run train.py
```

6. Review (and optionally modify) the plain-English task description in the local `PROGRAM.md`.

7. Start your AI agent (we used Claude Code with Claude Sonnet 5) in the selected project folder, with all permissions disabled, and launch the autonomous loop with the prompt in [How to Call the AI Agent](#how-to-call-the-ai-agent). During this phase the agent modifies only:

- `model.py`
- `train.py`

8. When the loop is finished, evaluate the saved fold checkpoints on the official test data:

```
uv run test.py
```

To evaluate the archived best-so-far snapshot instead of the most recent run:

```
uv run test.py --checkpoint-set best_so_far
```

9. Review the main outputs:

- `results.tsv`: validation results and the architectures or modelling choices tried across iterations
- `search_journal.md`: plain-English explanation of what was done at each iteration, why, and what to try next

## How to Call the AI Agent

Suggested prompt:

```
Have a look at `PROGRAM.md` and start a new autonomous experiment cycle. Do the setup first, then keep going autonomously after each completed run by inspecting the latest logs and updating model architectures in `model.py` and `train.py` for the next run. Keep commentary minimal: do not summarize `PROGRAM.md`, do not paste long logs or file contents, only provide brief progress updates when there is a meaningful state change or a blocker, and keep the final response concise. Do not create any loop script. `train.py` must remain a single-run trainer only. Before starting the runs, `results.tsv` should be empty or should not exist.

Important: `PROGRAM.md` explicitly encourages major modifications (e.g., trying physical models based on the literature, or mixing physical and black-box components). I am not looking for minor modifications that are only likely to produce limited improvements in the validation error.

Run at most 20 runs. Do not forget to create `results.tsv` and `search_journal.md`.
```

## Notes

- Each benchmark folder is its own `uv` project: run the environment setup from inside the selected subfolder, not from the repository root.
- Training runs were executed on a single NVIDIA RTX 3090 GPU. The agent itself runs remotely and performs no training.
- The test set is never accessed during the search and is used only once, to evaluate the retained model.
- You can modify `PROGRAM.md` and the agent prompt to make them specific to your problem, for example to instruct the agent to also try training paradigms beyond gradient-based simulation-error minimisation.
